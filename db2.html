同じSQLが、
ある日おそくなる。

昨日まで1秒で返っていた検索が、今日は30秒かかる。プログラムは1行も変えていない。——データベースは「どうやってデータを取りに行くか」を毎回自分で決めていて、その判断材料は統計情報、つまり表の中身を数えた記録です。記録が古びれば判断はずれます。それとは別に、表そのものが散らかっていれば、同じ行数を読むのに何倍もページをめくることになる。前者を直すのが RUNSTATS、後者を直すのが REORG。ここでは Db2 for LUW（Linux／UNIX／Windows）の話として進めます。

「おそくなる」までの道すじ——

  1. データが動くいま 毎日、行が足され、消され、更新されていく
  2. でも、統計をとったのは3か月前なので
  3. 古い数字で計画される見積もりのズレ 「10件しかない」つもりで選んだ方法で、100万件を処理してしまう
  4. それとは別に、表の中では
  5. 行が散らばるすきま・はみ出し 消した跡のすきま。更新であふれて、別ページに移った行
  6. どちらも、読むページ数を増やすので
  7. RUNSTATS数え直す いまの中身を数えて、カタログに書き直す。行は動かさない
  8. それでも詰まりが残るなら
  9. REORG並べ直す 生きている行を詰め直し、索引の順に並べ直す

「遅い＝索引が足りない」とはかぎりません。今日のいちばん大事なところは、遅くなる原因に情報の古さと置き方の乱れという別々の2種類がある、ということです。

なんで、こんな作業が要るの？

答えはシンプル。Db2が毎回、経路を自分で選んでいるから。

経路は、実行のたびに選び直される

SQLに書くのは「何がほしいか」だけで、「どう取りに行くか」は書きません。表を頭から全部読むのか、索引をたどるのか、どの表から先に読むのか——決めるのはオプティマイザという係です。

その判断材料が、表の行数・ページ数・列の値の散らばり・索引の状態。これらをまとめて統計情報と呼びます。

材料が古いと、堂々とまちがえる

統計は、RUNSTATSを流した瞬間の記録です。放っておいても勝手には新しくなりません。1万件に育った表を「10件」だと思っているオプティマイザは、10件向けのやり方を自信を持って選びます。

やっかいなのは、エラーにならないこと。ただ静かに遅くなるので、原因にたどりつくのに時間がかかります。

情報が正しくても、置き方は乱れる

行を削除しても、その跡地はすぐには詰まりません。更新で行が長くなると、元のページに入りきらず別ページへはみ出し、元の場所には印だけが残ります。

こうなると、同じ行数を読むのに触るページが増えます。これは統計を取り直しても1ミリも直りません。REORGの担当です。

RUNSTATS の5ステップ

詳しくオプションの選び方と、統計プロファイル

REORGには、2つのやり方がある

止めて一気にやるか、動かしながら少しずつやるか。

まとめてやる（classic／オフライン）

生きている行だけを別の場所へ順にコピーし、すきまなく詰め直して、最後に元の表と置きかえます。索引は、そのあとに作り直されます。短い時間できれいに片づくのが持ち味です。

そのかわり、実行中の更新は待たされます（ALLOW READ ACCESS を指定すれば読み取りは通せます）。作業用に表と同じくらいの空きが要り、USE で一時表スペースを指定できます。

動かしながらやる（INPLACE／オンライン）

表の中で行を少しずつ動かして、すきまを埋めていきます。読み書きを止めません。途中で PAUSE して、あとで RESUME することもできます。

そのかわり時間がかかり、ログを多く使います。索引は作り直されないので、終わったあとに REORG INDEXES を別に流すのがふつうです。

索引だけ、片づける

削除が多い表では、詰まっているのは索引のほうです。索引のページには、消された行の跡（擬似削除）がたまっていきます。

REORG INDEXES ALL FOR TABLE … で作り直す、CLEANUP を指定して跡地の掃除だけに留める、といった選び方ができます。表は動かさないので軽く済みます。

まとめてやるとき、中で動く4つの段階

詳しく書き方と、進み具合の見方

やるかどうかは、測ってから決める

勘でやらない。Db2には、判定するためのコマンドがあります。

REORGCHK は、統計から計算した8つの式で「基準から外れているか」を出します。表について3つ（F1〜F3）、索引について5つ（F4〜F8）。出力の REORG 欄は式の数だけ文字が並び、- なら範囲内、* なら外れている印です。

-- いまある統計だけで判定する（表は読まないので軽い）
db2 "REORGCHK CURRENT STATISTICS ON TABLE SALES.ORDERS"

Table statistics:
  TABLE            CARD     OV     NP     FP    F1    F2    F3  REORG
  SALES.ORDERS  1200000   8400   9800  14200   0.7    68    69  -**

この表は F1は合格、F2とF3が外れている状態です。はみ出した行は0.7%しかないのに、ページの中身が68%しか詰まっておらず（F2は70%以上がめやす）、確保した14,200ページのうち9,800ページ、つまり69%しか使っていない（F3は80%以上がめやす）。大量に削除したあとの、典型的な姿です。

  1. F1 は「はみ出した行の割合」。更新で行が長くなり、別ページへ移った行がどれだけあるか。多いなら、読むページ数が余計に増えています。
  2. F2 は「ページの詰まり具合」。データページの中が、どれだけ実際に使われているか。削除の跡が残っていると下がります。
  3. F3 は「確保した場所の使用率」。表のために確保したページのうち、実際に使っているページの割合。空きページを抱えたままだと下がります。
  4. * が付いた＝必ずREORG、ではありません。式はあくまで目安です。かかる時間・ログ・止まる時間と釣り合うかを見て、最後は人が決めます。
詳しく8つの式の意味と、索引側のF4〜F8

じつは、自動でもやってくれる

手で流す前に、まず自動保守の設定を見にいきましょう。

親のスイッチから、順に入れる

AUTO_MAINT がすべての親です。その下に AUTO_TBL_MAINT（表の保守）があり、さらにその下に AUTO_RUNSTATS と AUTO_REORG が並びます。

上のスイッチがOFFなら、下をONにしても動きません。「自動にしているはずなのに動いていない」の原因は、たいていここです。

統計は、走りながらでも直せる

AUTO_STMT_STATS（リアルタイム統計）を入れると、SQLをコンパイルする時点で「この表の統計は古すぎる」と判断されたときに、その場で小さく統計を集めます。

効かせるには AUTO_MAINT／AUTO_TBL_MAINT／AUTO_RUNSTATS／AUTO_STMT_STATS の4つが、すべてONである必要があります。

動いてよい時間帯を、決めておく

自動RUNSTATSはオンライン保守ウィンドウの中で動き、自動REORGはオフライン保守ウィンドウの中だけで動きます。

「この時間帯なら止めてよい」を先に決めておかないと、自動REORGは順番が回ってきても実行されないまま、いつまでも待ち続けます。

詳しく設定の入れ方と、任せ方のさじ加減

順番を、まちがえない

この3つは、必ずこの順です。

  1. まず REORG（並べ直す）。行の物理的な位置も、索引の形も変わります。つまり、いま持っている統計は「並べ直す前の姿」の記録になり、実態と合わなくなります。
  2. つぎに RUNSTATS（数え直す）。並べ直したあとの姿を数えます。逆順でやると、せっかく取った統計をREORGで古くしてしまうことになります。
  3. 最後に REBIND（計画を作り直す）。静的SQLのパッケージは、作られた時点の計画を持ち続けます。新しい統計で選び直させるには REBIND が必要です。動的SQLはキャッシュされた計画が無効になるので、次の実行で自動的に選び直されます。

クイズ：きみは何問わかる？

全5問。まちがえても大丈夫、答えのほうが面白い。

気をつけないと、痛い目にあう

相手は、動いている本番のデータです。

  1. 大きな表のオフラインREORGは、終わる時間が読めない。何億行もある表を止めて並べ直すと、終わるまで更新は通りません。同じくらいの大きさの環境で、先に時間を測ってから計画します。
  2. 場所とログを、先に見積もる。classic REORG は表と索引のコピーぶんの空きが要ります（既定では同じ表スペース、USE で一時表スペースを指定可）。INPLACE は動かした行のぶんログを書き続けるので、ログがあふれるとそこで止まります。
  3. 統計をとるだけなら、止めなくていい。RUNSTATS は既定で読み書きを止めません（ALLOW WRITE ACCESS）。「重いから夜間に」と決めつける前に、UTIL_IMPACT_PRIORITY で優先度を下げて流す手もあります。
  4. 全部の表に、毎晩フルでかけない。数千の表へ無条件にRUNSTATSを回すと、それ自体が負荷になります。更新の多い表、大きく増減した表にしぼります。
  5. 統計を「よく見せよう」として、手で書きかえない。SYSSTAT のビュー経由で統計を更新することはできますが、実態と違う数字を入れると、その表を使う全部のSQLが引きずられます。検証用と割り切る場所です。
  6. 索引だけで足りることも多い。表全体を止めて並べ直す前に、REORG INDEXES で足りないかを確かめます。削除が多い表では、詰まっているのは索引のほうです。

ことばのミニ辞典

この先どこかで見かけたときのために。

統計情報
表・列・索引の状態を数えた記録。行数、ページ数、値の異なり数など。カタログ表に置かれ、オプティマイザだけが読む。
オプティマイザ
SQLをどの経路で実行するかを決める係。同じSQLでも、統計が変われば選ぶ経路は変わる。
アクセスプラン
オプティマイザが選んだ実行の段取り。表を全部読むか、索引をたどるか、どの表から結合するか。
カーディナリティ
件数のこと。表の行数は CARD、列に入っている値の異なり数は COLCARD として記録される。
分布統計
列の値の偏りの記録。WITH DISTRIBUTION を付けると集める。「特定の値だけ極端に多い」列で効く。
クラスター率（CLUSTERRATIO）
索引の並び順と、実データの並び順がどれだけ一致しているか。低いと、索引をたどるたびに飛び飛びのページを読むことになる。
オーバーフロー行
更新で長くなり、元のページに入りきらず別ページへ移った行。元の場所には印だけが残るので、読むページが増える。
擬似削除（pseudo-deleted）
索引の中で「消した」と印を付けただけの状態。領域はまだ残っていて、掃除しないとたまり続ける。
REORGCHK
統計から8つの式を計算し、REORGすべきかを判定するコマンド。出力の * は、その式が推奨範囲から外れている印。
統計プロファイル
「この表はこの取り方で」をDb2に登録しておく仕組み。SET PROFILE で登録し、次回からは USE PROFILE だけで同じ取り方を再現できる。
REBIND
静的SQLのパッケージに、いまの統計で計画を選び直させる操作。動的SQLは、キャッシュが無効化されるので自動で選び直される。
保守ウィンドウ
自動保守が動いてよい時間帯。オンライン用とオフライン用があり、自動REORGは後者の中だけで動く。

1. 統計は、どこに書かれているのか

やさしい説明の「なんで、こんな作業が要るの？」の部分

RUNSTATSが書き込む先は、Db2が自分で持っているカタログ表です。人が読める形で置かれているので、SQLでそのまま確認できます。おもな置き場所は4つです。

SYSCAT.TABLES表そのものの数字。CARD（行数）、NPAGES（使用ページ）、FPAGES（確保ページ）、OVERFLOW（はみ出した行）、STATS_TIME（いつ取ったか）
SYSCAT.COLUMNS列ごとの数字。COLCARD（異なり数）、HIGH2KEY／LOW2KEY、NUMNULLS、AVGCOLLEN
SYSCAT.INDEXES索引の数字。CLUSTERRATIO、NLEAF（葉ページ数）、NLEVELS（段数）、FIRSTKEYCARD、FULLKEYCARD
SYSCAT.COLDIST分布統計。よく出る値（頻出値）と、値をならべて区切った位置（分位）が入る

まず見るのは、いつ取ったか

SELECT TABNAME, CARD, NPAGES, FPAGES, OVERFLOW, STATS_TIME
  FROM SYSCAT.TABLES
 WHERE TABSCHEMA = 'SALES' AND TYPE = 'T'
 ORDER BY CARD DESC;

STATS_TIME が NULL なら、その表は一度も統計を取っていません（あるいはリセットされています）。「遅い」と言われたとき、最初に見るのはここです。日付が半年前なら、それだけで疑う理由になります。

HIGH2KEY が「2番目」なのはなぜか

列の最大値・最小値ではなく、2番目に大きい値・2番目に小さい値を記録しています。いちばん端の値は、テストで入れた 9999-12-31 のような外れ値であることが多く、それを範囲の端として信じると、範囲検索の見積もりが大きく狂うからです。

手で書きかえることも、できてしまう

SYSSTAT.TABLES・SYSSTAT.COLUMNS などのビューは更新可能で、統計の値を直接書きかえられます。「本番と同じ規模の統計を、小さな検証環境に持ち込んで実行計画だけ再現する」といった使い方をします。

本番で実態と違う値を入れると、その表を使うすべてのSQLの計画が引きずられます。しかも原因が見えにくい。使うなら、検証環境だけにしてください。

2. RUNSTATSの書き方

やさしい説明の「RUNSTATSは、1回で何をしているか」の部分

迷ったときの基本形はこれです。表の統計・列の分布・索引の詳細を、まとめて取ります。

RUNSTATS ON TABLE SALES.ORDERS
   WITH DISTRIBUTION AND DETAILED INDEXES ALL;

おもなオプション

WITH DISTRIBUTION値の偏りまで記録する。「都道府県のうち東京だけで6割」のような列があるとき、これがないと値が均等に散っていると仮定される
AND INDEXES ALL表の統計に加えて、すべての索引の統計も同時に取る
AND DETAILED INDEXES ALL索引について、ページの読み方まで細かく見積もる。大きな索引ほど効く
AND SAMPLED DETAILED INDEXES ALL上をサンプリングで軽くしたもの。索引が巨大なときの逃げ道
ON KEY COLUMNS索引の先頭列など、キーになる列にしぼって列統計を取る。列が非常に多い表で効く
TABLESAMPLE SYSTEM(10)表の10%だけ読んで推定する（ページ単位の抽出）。BERNOULLI は行単位
ALLOW WRITE ACCESS実行中も他から読み書きできる。これが既定。ALLOW READ ACCESS にすると更新が待たされる
UTIL_IMPACT_PRIORITY nほかの処理への影響を抑えて流す。数字が小さいほど遠慮する（省略時は制限なし）
SET PROFILE / USE PROFILE取り方を登録しておき、次回からはそれを再現する

統計プロファイル

表ごとに「この表はこの取り方で」を登録しておけます。長いオプションを毎回書かなくてよくなり、自動RUNSTATSもこのプロファイルに従うようになります。

-- 取り方を登録して、そのまま実行する
RUNSTATS ON TABLE SALES.ORDERS
   WITH DISTRIBUTION AND DETAILED INDEXES ALL SET PROFILE;

-- 登録だけして、実行はしない
RUNSTATS ON TABLE SALES.ORDERS ... SET PROFILE ONLY;

-- 次回からは、これだけでよい
RUNSTATS ON TABLE SALES.ORDERS USE PROFILE;

どこまで取るか、の目安

  • 検索条件・結合条件・ORDER BY に出てくる列は、統計があるほど効きます
  • 値が偏っている列には WITH DISTRIBUTION を付けます
  • 表がそれほど大きくないなら、迷わず WITH DISTRIBUTION AND DETAILED INDEXES ALL で構いません
  • 巨大な表は TABLESAMPLE と SAMPLED で時間を抑えます。精度は少し落ちますが、古い統計よりはるかにましです

RUNSTATSを流したあと、静的SQL（プログラムに埋め込んで作ったパッケージ）は REBIND するまで古い計画のままです。「統計を取り直したのに速くならない」の原因の定番がこれです。

3. REORGの書き方と、選び方

やさしい説明の「REORGには、2つのやり方がある」の部分

まとめて（classic）動かしながら（INPLACE）
書き方REORG TABLE TREORG TABLE T INPLACE
更新止まる（ALLOW READ ACCESS で読み取りは可）止まらない
索引最後にまとめて作り直される作り直されない（別途 REORG INDEXES）
時間短い長い
場所表と同じくらいの作業領域が要る表の中で動かす
ログ比較的少ない多い
中断できない（やり直し）PAUSE／RESUME できる
-- まとめて。索引の順に並べ直し、作業は一時表スペースで
REORG TABLE SALES.ORDERS INDEX SALES.IX_ORD_DATE
   USE TEMPSPACE1 ALLOW READ ACCESS;

-- 動かしながら。索引はあとで別に片づける
REORG TABLE SALES.ORDERS INPLACE ALLOW WRITE ACCESS START;
REORG INDEXES ALL FOR TABLE SALES.ORDERS ALLOW WRITE ACCESS;

INDEX 句を付けるかどうか

INDEX を指定すると、その索引のキー順に行を並べ直します。範囲検索でよく使う索引を指定すると、クラスター率（CLUSTERRATIO）が上がり、続けて読むページが連続します。指定しなければ、いまの並びのまま、すきまだけを詰めます。

軽い選択肢もある

  • RECLAIM EXTENTS：空になったエクステントを表スペースに返すだけ。行は動かさないので軽い
  • CLEANUP ONLY／CLEANUP ONLY PAGES（索引）：作り直さず、跡地の掃除だけをする
  • REORG INDEXES ALL FOR TABLE …：表はそのまま、索引だけを作り直す。オンラインでやりたいときは ALLOW READ ACCESS か ALLOW WRITE ACCESS を明示する

進み具合の見方

db2pd -db SAMPLE -reorgs
db2 "LIST HISTORY REORG ALL FOR DB SAMPLE"

classic REORG の内部の段階（並べ替え → 作り直し → 置きかえ → 索引の再作成）は、この出力に現れます。長時間かかっているときに「いまどの段階か」を見れば、あとどれくらいかの見当がつきます。

INPLACE のあとに索引を放っておくと、「表はきれいなのに、索引を使う検索だけ遅い」という状態が残ります。セットで流してください。

4. REORGCHK の8つの式

やさしい説明の「やるかどうかは、測ってから決める」の部分

表について（F1〜F3）

F1100 × OVERFLOW ÷ CARD < 5
はみ出した行が5%未満か
F2100 × (データページの実質使用量) > 70
ページの中身が7割以上詰まっているか
F3100 × (使用ページ ÷ 確保ページ) > 80
確保した場所の8割以上を、実際に使っているか

索引について（F4〜F8）

F4CLUSTERRATIO（または正規化した CLUSTERFACTOR） > 80
索引の順と実データの順が、8割以上そろっているか
F5100 × (葉ページで使われている領域 ÷ 空でない葉ページの利用可能領域) > MIN(50, 100 − PCTFREE)
葉ページがすかすかになっていないか
F6(100 − PCTFREE) × (段を1つ減らした索引に入る領域 ÷ 全キーに必要な領域) < 100
段数が、必要より1つ多くなっていないか
F7100 × (擬似削除されたRID数 ÷ 全RID数) < 20
消した跡が、たまりすぎていないか
F8100 × (擬似的に空の葉ページ数 ÷ 全葉ページ数) < 20
中身のない葉ページが、残りすぎていないか

どこが外れたら、何をするか

  • F1・F2・F3 が外れている → 表のREORG。すきまとはみ出しを詰め直す
  • F4 が外れている → INDEX 句を付けたREORG。並び順をそろえ直す
  • F5・F6 が外れている → 索引の作り直し（REORG INDEXES ALL）
  • F7・F8 が外れている → 跡地の掃除（CLEANUP）で足りることが多い

2つのモードと、表で受け取る方法

-- いまある統計だけで判定する（軽い）
REORGCHK CURRENT STATISTICS ON TABLE SALES.ORDERS;

-- 統計を取り直してから判定する（重い）
REORGCHK UPDATE STATISTICS ON SCHEMA SALES;

-- 結果を表として受け取り、自分のしきい値で判定する
CALL SYSPROC.REORGCHK_TB_STATS('T', 'SALES.ORDERS');
CALL SYSPROC.REORGCHK_IX_STATS('T', 'SALES.ORDERS');

UPDATE STATISTICS 版は、内部でRUNSTATS相当を流します。スキーマ全体に対して日中に軽い気持ちでかけると、それ自体が重い処理になります。

5. 自動保守に、どこまで任せるか

やさしい説明の「じつは、自動でもやってくれる」の部分

スイッチは、親子になっている

AUTO_MAINT                  ← すべての親
 ├ AUTO_DB_BACKUP           自動バックアップ
 └ AUTO_TBL_MAINT           表の保守の親
    ├ AUTO_RUNSTATS         自動で統計を取る
    │   ├ AUTO_STMT_STATS   SQLのコンパイル時に、その場で取る
    │   └ AUTO_SAMPLING     大きな表はサンプリングで取る
    └ AUTO_REORG            自動で再編成する
db2 UPDATE DB CFG FOR SAMPLE USING AUTO_MAINT ON
db2 UPDATE DB CFG FOR SAMPLE USING AUTO_TBL_MAINT ON
db2 UPDATE DB CFG FOR SAMPLE USING AUTO_RUNSTATS ON
db2 UPDATE DB CFG FOR SAMPLE USING AUTO_STMT_STATS ON
db2 UPDATE DB CFG FOR SAMPLE USING AUTO_REORG ON

-- いまの状態を確かめる
db2 GET DB CFG FOR SAMPLE | grep -i auto

動く時間帯

自動RUNSTATSはオンライン保守ウィンドウ、自動REORGはオフライン保守ウィンドウの中でだけ動きます。ウィンドウは自動保守ポリシーで決めます（SYSPROC.AUTOMAINT_SET_POLICY などで設定）。オフラインのウィンドウを1分も用意していなければ、自動REORGは永遠に動きません。

任せ方のさじ加減

  • 自動RUNSTATSは「大きく変わった表」を自分で選んで流します。全表を毎晩なめるわけではありません
  • 特定の表だけ取り方を変えたいときは、統計プロファイルを登録しておきます。自動RUNSTATSもそれに従います
  • 自動が何を評価して、何を見送ったかは db2diag.log に残ります。「動いていない気がする」ときは、まずここを読みます
  • 止まってはいけない表のREORGは、自動に任せず、止められる時間帯に手で流す判断もありです

6. いつ、どこまでやるか

運用の組み立て方

流すべきタイミング

  • 大量ロード・大量削除の直後。件数が桁で変わったときは、統計も必ず取り直す
  • 索引を新しく作ったあと
  • 列の追加など、表の定義を変えたあと
  • 定期的に（週次・月次）。ただし全表ではなく、変化した表だけを選ぶ

判断の材料

SYSCAT.TABLES.STATS_TIMEいつ統計を取ったか。古い順に並べれば、放置されている表が見つかる
REORGCHK の REORG 欄どの式が外れているか。表を直すのか索引を直すのかが分かれる
SYSIBMADM.ADMINTABINFO実際に使っている領域と、再利用できる領域。REORGでどれだけ減るかの見当がつく
EXPLAIN／db2exfmt計画上の見積もり行数と、実際の行数の差。ここが桁で違えば、統計を疑う

やらないほうがよいこと

  • 数百行しかない小さな表に、毎晩REORGをかける（効果より手間のほうが大きい）
  • 増える一方で削除のない表に、頻繁なREORG（すきまができないので、詰め直すものがない）
  • ピーク時間帯の REORGCHK UPDATE STATISTICS
  • 本番でいきなり初めて試すこと。実行時間・ログ量・必要な空き容量を、同じ規模の環境で先に測る

RUNSTATSとREORGは、速くするための魔法ではありません。「オプティマイザに正しい材料を渡し、無駄なページを読ませない」という当たり前の状態に戻す作業です。それでも遅いなら、次に疑うのはSQLと索引設計のほうです。
