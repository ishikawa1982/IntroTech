WebSocketのしくみ v1.1.1 ← 用語集トップ

「まだ？」と
聞きに行かなくてよくなった日。

チャットで相手がメッセージを送ると、こちらの画面にすぐ出てくる。ページを更新していないのに、なぜ届くんだろう。ふつうのWebのしくみでは、こちらから聞きに行かないと何ももらえないはずなのに。その答えが WebSocket。

チャット画面をひらいてから、メッセージが届くまで——

  1. ブラウザいま チャットのページをひらいた
  2. まずは、ふつうに話しかける
  3. あいさつふつうのHTTP 「電話に切りかえてもいい？」とお願いする
  4. サーバーがOKを返すと
  5. 回線がつながる1回だけ ここから先は、手紙ではなく電話になる
  6. つなぎっぱなしのまま
  7. どっちからでもいつでも 相手が発言した瞬間、サーバーから届く

ふつうのWebが「手紙のやりとり」なら、WebSocketはつなぎっぱなしの電話。これが今日のいちばん大事なところ。

なんで、こんなものが必要になったの？

答えはシンプル。Webは、聞かれるまで話しかけてこないから。

ふつうのWebは「注文して、受け取る」だけ

ページを見るとき、ブラウザが「このページをください」と頼み、サーバーが返す。返したら、そこで会話は終わり。店員は、こちらが声をかけるまで何も言ってこない。

この「頼まれたら答える」やり方が HTTP。シンプルで丈夫だけど、サーバーの側から急に話しかけることはできない。

だから、しつこく聞きに行っていた

新着メッセージを表示したい。でもサーバーからは言ってくれない。ならばどうするか——5秒おきに「新しいの、ある？」と聞きに行く。答えはたいてい「ないよ」。

これをポーリングと呼ぶ。1人でも1時間に720回。1000人いれば72万回。ほとんどが空振りなのに、聞くたびに毎回あいさつからやり直している。

それなら、つなぎっぱなしにすればいい

最初に1回だけ「これから電話にします」と約束して、そのまま回線を保つ。用があるときだけ、どちらからでも話しかける。

これがWebSocket。空振りの「ある？」「ないよ」がまるごと消えて、しかも新着が出た瞬間に届くようになった。

ボタンで切りかえて、矢印の数を見てみよう。

で、いつ使えばいいの？

つなぎっぱなしは便利だけど、なんでもこれにすればいいわけじゃない。

向いているもの

チャット、対戦ゲーム、共同編集、株価やセンサーの表示、通知。サーバーの側から急に知らせたいもの、あるいは秒より速いやりとりが要るもの。

共通点は「いつ起きるか、こちらには予測できない」こと。予測できないなら、待つしかない。

向いていないもの

ふつうのページ表示、記事の読み込み、フォームの送信。頼めば答えが返ってくるものは、HTTPのままでいい。

つなぎっぱなしは、サーバー側が全員ぶんの回線を覚えておくということ。人数が増えると、それ自体が重さになる。

似た仲間もいる

サーバーから送るだけでいいなら SSE（Server-Sent Events）という軽い方法もある。こちらはHTTPのまま使えて、切れたときの復帰も楽。

両方向にどんどん流すなら WebSocket、届けるのが一方通行なら SSE。用途で選ぶ。

詳しくサーバーが何台もあるとき、何が起きるのか

クイズ：きみは何問わかる？

全5問。まちがえても大丈夫、答えのほうが面白い。

気をつけないと、あとで泣く

つなぎっぱなしには、つなぎっぱなしなりの苦労がある。

  1. 回線は、かならず切れる。電車でトンネルに入る、Wi-Fiが切りかわる、パソコンが眠る。切れない前提で作ると、ある日ぱったり動かなくなる。
  2. 切れたら、自分でつなぎ直す。再接続のしくみは自分で書く。すぐ何度も試すとサーバーが潰れるので、少しずつ間隔をのばしながら試すのが定番。
  3. 切れているあいだの分を、どう埋めるか。つながっていない時間に届いたメッセージは、そのままでは受け取れない。「どこまで受け取ったか」を覚えておいて、あとから取り直す。
  4. 生きているか、ときどき確かめる。回線は、切れたことに気づかないまま死んでいることがある。定期的に小さな合図（ping／pong）を送り合って確認する。
  5. 誰なのかを、最初に確かめる。つないだあとはずっと同じ相手として扱われる。最初のあいさつの時点で、ちゃんと本人か確かめておく。
  6. 鍵をかける。アドレスは ws:// ではなく wss:// を使う。中身が丸見えにならないようにする、いつもの話。

1. ハンドシェイクの中身

やさしい説明の「電話に切りかえていい？」の部分

WebSocketの接続は、ふつうのHTTP/1.1リクエストとして始まります。クライアントが送るのはこれだけです。

GET /chat HTTP/1.1
Host: example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13

サーバーが対応していれば、200 ではなく 101 が返ります。この時点で、同じTCP接続の上を流れるものがHTTPからWebSocketに変わります。

HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=

Sec-WebSocket-Key は暗号ではない

クライアントが送るのはランダムな16バイトのBase64。サーバーはこれに仕様で決められた固定の文字列をつなげ、SHA-1をかけてBase64にしたものを Sec-WebSocket-Accept として返します。計算方法は公開されているので、秘密の共有にはなりません。

目的は「相手がWebSocketを理解しているサーバーかどうか」の確認です。仕組みを知らないキャッシュやプロキシが、たまたま 101 らしきものを返してしまう事故を防いでいます。

覚えておくとよいヘッダ

  • Sec-WebSocket-Version: 13 — 現行のバージョン。これ以外はまず出てきません。
  • Sec-WebSocket-Protocol — アプリ独自の「話し方」の名前を候補として並べ、サーバーが1つ選んで返します。バージョン違いを共存させるときに使えます。
  • Sec-WebSocket-Extensions — 圧縮（permessage-deflate）などの拡張の合意に使います。
  • Origin — どのサイトから接続されたか。サーバー側で必ず検査します（理由は5章）。

握手に失敗した場合は、ただのHTTPエラーレスポンスが返るだけです。だから 404 や 401 をそのまま使えます。

2. フレーム — 1通ぶんの構造

やさしい説明の「1通ぶんがとても軽い」の部分

握手が終わったあと流れるのは、HTTPのメッセージではなくフレームという小さな単位です。ヘッダは2〜14バイト。HTTPリクエストのヘッダが数百バイト〜数KBあることを思えば、桁がちがいます。ポーリングが重かったのは、往復の回数だけでなく、毎回このヘッダとTLSの処理を積み直していたからでもあります。

opcode（この1通は何なのか）

0x1テキスト（UTF-8であることが必須）
0x2バイナリ
0x0継続。分割された続きのフレーム
0x8Close（終わりのあいさつ）
0x9 / 0xAPing / Pong（生存確認）

メッセージの切れ目が保たれる

TCPは「バイトの川」なので、生のTCPを使うと自分で切れ目を決める必要があります。WebSocketは FIN ビットで1メッセージの終わりを示すため、受け取る側には1メッセージ単位で届きます。大きなデータは複数フレームに分割して送れて、受信側では1つにまとめて渡されます。

マスキング

クライアントからサーバーへ送るフレームは、ランダムな4バイトの鍵でXORをかけることが仕様で義務づけられています。暗号のためではなく、中継するプロキシに「これはHTTPリクエストだ」と誤解させないためです。逆向き（サーバー→クライアント）にマスクは要りません。

ブラウザやライブラリが自動でやってくれる部分なので、自分で書く場面はほぼありません。ただしパケットを覗いたとき「中身が読めない」のはこれが理由です。

3. 何の上を流れているのか

やさしい説明の「ミニ辞典」の背景

WebSocketはTCPの上に直接乗っています。wss:// の場合はTLSの上。ポートは ws:// が80、wss:// が443で、HTTPと同じです。企業のファイアウォールを通りやすいのは、この設計のおかげです。

途中の機械に注意

  • ロードバランサ／リバースプロキシ — Upgrade ヘッダを素通しする設定が必要です。設定を忘れると、握手が 400 や 200 で失敗します。
  • アイドルタイムアウト — 何も流れない接続を一定時間で切る設定がよくあります（既定60秒などが多い）。ハートビートを送る実務的な理由の半分はこれです。
  • バッファリングするプロキシ — レスポンスを溜めてから返す設定だと、リアルタイム性が壊れます。

HTTP/2・HTTP/3との関係

WebSocketの握手はHTTP/1.1が前提です。HTTP/2の上で使うには Extended CONNECT という別の仕組み（RFC 8441）が必要で、対応状況は環境によってまちまちです。「HTTP/2にしたらWebSocketが繋がらなくなった」は、わりとよくある事故です。

4. 切断と再接続の設計

やさしい説明の「回線の一生」の部分

クローズコードを見る

1000正常終了。どちらかが意図して閉じた
1001離脱。ページを閉じた、サーバーが停止する など
1006異常終了。Closeフレームすら届かなかった＝ネットワーク断。実務でいちばん見る番号
1011サーバー内部エラー
4000〜4999アプリが自由に決めてよい範囲。「トークン失効」などを自前で定義する

1006 と 1000 を区別できると、「再接続すべきか、あきらめるべきか」の判断が書けます。

再接続は、ばらけさせる

サーバーを再起動すると全員が同時に切れます。全員がすぐ再接続すると、起動直後のサーバーに接続要求が集中して、また落ちます。指数バックオフ（1秒→2秒→4秒…）に加えて、待ち時間へランダムなゆらぎを足すのが定石です。

ハートビート

プロトコルにはPing/Pongがありますが、ブラウザのJavaScriptからは送れません（受け取ったPingに自動でPongを返すだけ）。そのため、アプリ独自の小さなメッセージを定期的に送り合う形が一般的です。相手が黙って死んでいる状態を検知できます。

取りこぼしをどう埋めるか

切れているあいだに発生したメッセージは、当然届きません。実装としては、受信済みの最後のIDや時刻を覚えておき、再接続時に「そこから先をください」とHTTPで取り直すのが素直です。WebSocketは「今この瞬間」を運ぶもので、履歴の保証は別のしくみで持つ、と分けて考えます。

送りすぎの検知

受信側の回線が細いと、送信データが手元に溜まります。ブラウザでは bufferedAmount で溜まり具合がわかるので、一定量を超えたら送信を間引く、といった制御ができます。

5. 認証とセキュリティ

やさしい説明の「誰なのかを確かめる」の部分

Authorizationヘッダが使えない

ブラウザの WebSocket は、コンストラクタでカスタムヘッダを指定できません。普段のAPI呼び出しと同じ感覚で書こうとすると、まずここで詰まります。実務での回避策は3つ。

  • Cookie — 握手はHTTPリクエストなので、Cookieは自動で送られます。素直ですが SameSite の挙動に注意。
  • 接続後の最初のメッセージで認証 — つないだ直後に認証メッセージを送らせ、それまでは何も購読させない。ログに残らず、失効も扱いやすい。
  • URLのクエリにトークン — 手軽ですが、アクセスログや履歴に残ります。使うなら短命なワンタイムのトークンに限ります。

Originの検査は必須

WebSocketには同一生成元ポリシーが適用されません。つまり evil.example のページから、あなたのサーバーへ接続を張れます。Cookie認証だけに頼っていると、利用者のログイン状態を勝手に使われます（Cross-Site WebSocket Hijacking）。Origin ヘッダをサーバー側で確認し、許可したドメイン以外は握手の時点で断ります。

接続時だけでなく、毎回確かめる

接続は長く生き続けます。「このチャンネルを購読したい」といった要求が来るたびに権限を確認しないと、つないだ時点の権限のまま何時間も居座られます。トークンの有効期限が切れたら、こちらから閉じる設計にしておきます。

6. スケールと運用

やさしい説明の「向いていないもの」の背景

接続は「状態」

HTTPは1回ごとに完結するので、どのサーバーが処理してもかまいません。WebSocketは違います。利用者Aは1号機に、利用者Bは2号機につながっている——この状態がずっと残ります。1台あたりの上限は、ファイルディスクリプタ数と、1接続あたりのメモリ（数十KB程度）で決まります。

サーバーをまたいだ配信

AがBにメッセージを送るとき、Bが別のサーバーにつながっていたら届きません。サーバー間に橋を架ける必要があります。Redis の Pub/Sub や NATS、Kafka などを挟み、「自分につながっている人だけに配る」形にするのが定番です。この橋が、WebSocketを本番で使うときの実質的な設計の中心になります。

デプロイのたびに全員切れる

サーバーを入れ替えれば接続は切れます。切る前にクローズフレームを送って理由を伝える、順番にサーバーを入れ替える、再接続の待ち時間をばらけさせる。このあたりを用意していないと、リリースのたびにアクセスの山ができます。

選択肢の比較

WebSocketSSEロングポーリング
向き双方向サーバー→クライアント双方向（疑似）
土台専用（握手はHTTP）HTTPのままHTTPのまま

「サーバーから知らせたいだけ」なら、SSEのほうが作りも運用も軽くすみます。双方向が本当に要るのかを先に確かめると、あとが楽になります。
