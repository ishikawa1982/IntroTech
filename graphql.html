GraphQLのしくみ v1.0.0 ← 用語集トップ

ほしい形を、
こちらから書く。

これまでのAPIでは、返ってくる形を決めるのはサーバーでした。窓口ごとに中身が決まっていて、こちらはそれを受け取るだけ。GraphQL は、その役目を入れかえます。ほしいものの形をこちら（クライアント）が文章で書いて送り、サーバーはその形のまま返す。2015年に仕様が公開された、APIのための問い合わせ言語です。

「形を書いて送る」にたどりつくまで——

  1. 画面が増えるいま 画面ごとに、ほしい項目の組み合わせが変わっていく
  2. でも、返る形はサーバーが決めているので
  3. 多すぎる／足りない過不足 使わない項目までついてくる。逆に足りなくて、何度も往復する
  4. 画面に合わせて窓口を足していくと
  5. 窓口が増え続ける消せない 似たようなAPIが並び、誰が使っているか分からなくなる
  6. だったら、形を決める役をわたしてしまおう
  7. ほしい形を書いて送るクエリ サーバーは、送られてきた形のとおりに組み立てて返す
  8. ただし、何でも書けては困るので
  9. 型で、書ける範囲を決めるスキーマ 書けるのは型に載っていることだけ。実行する前に確かめられる

GraphQLは「速いAPI」ではありません。形を決める役を、サーバーからクライアントへ渡したAPIです。

なんで、こんなものが生まれたの？

答えはシンプル。画面がほしい形と、APIが返す形は、いつもズレるから。

多すぎる — 使わない項目まで、ついてくる

「ユーザー1件」の窓口をたたくと、登録日も設定も権限も、ぜんぶまとめて返ってきます。画面が使うのは名前と写真の2つだけなのに。

定食しかない食堂のようなもの。ごはんだけ欲しくても、小鉢も汁物もついてきて、そのぶん待たされます。

足りない — 1回では終わらず、何度も往復する

逆もあります。本の情報を取り、その中の著者IDでもう1回、レビューを出すのにもう1回。前の答えを見ないと次が投げられないので、往復が直列につながります。

回線が遠いほど、この「1往復」が重くのしかかります。項目が足りないのではなく、取りに行く回数が足りていない状態です。

窓口が増える — そして、消せなくなる

過不足をなくそうとすると、画面ごとの専用APIを足すことになります。似た窓口が並び、どれを誰が使っているか分からなくなり、こわくて消せません。

「v2を作る」という手もありますが、それはv1を永久に運び続ける約束でもあります。GraphQLがバージョンを切らない方向へ進んだのは、ここが出発点です。

書ける範囲は、型で決まっている

クライアントが何でも書けるわけではありません。書けるのはスキーマに載っていることだけです。

スキーマは、このAPIに何があるかを書いた設計図です。言語に依存しない書き方（SDL）で書くと、こう見えます。

type Query {            # ここが入口。すべてはここから始まる
  book(id: ID!): Book
  viewer: User
}

type Book {
  id: ID!
  title: String!       # ! は「null にならない」という約束
  year: Int             # ! が無ければ、null かもしれない
  author: Author        # 型が型を指す。ここでグラフになる
  reviews: [Review!]!  # [ ] はリスト
}

type Author {
  name: String!
  country: String
}

Book が Author を指し、Author がまた別の型を指す。この「型が型を指す」つながりがグラフになっていて、クライアントはそこをたどって一度に取ってこられます。GraphQL の名前の由来はここです。

名前のつく型は、6種類しかない

加えて、型そのものではなく型に付ける「修飾子」が2つあります。!（null にしない）と [ ]（リストにする）です。[Review!]! は「リスト自体もnullにならないし、中身にもnullは入らない」という意味になります。

詳しく! と [ ] の組み合わせ、抽象型の使い分け

入口は3つ

読む・書く・受け取り続ける。どれも同じ書き方ですが、実行のされ方が違います。

query — 読む

データを取ってくる操作です。書かれたフィールドは並列に解決してかまわないことになっているので、サーバーは順番を気にせず同時に処理できます。

先頭の query は省略できます（{ book { title } } だけでも通ります）。ただし変数を使うときや、名前をつけるときは省略できません。

mutation — 書く

作る・変える・消す操作です。仕様では、副作用を持ってよいのは mutation のいちばん外側のフィールドだけと決められています。そしてそれらは上から順に1つずつ（直列に）実行されます。

直列なだけで、トランザクションではありません。1つ目が成功して2つ目が失敗したとき、1つ目を取り消すしくみは GraphQL 側にはありません。

subscription — 受け取り続ける

「新しいレビューが付いたら教えて」のように、つなぎっぱなしで更新を受け取る操作です。1つの操作に書けるルートのフィールドは1つだけと決まっています。

どの通信路を使うかは仕様の外。実際には WebSocket や Server-Sent Events に載せることがほとんどです。

詳しくN+1のつぶし方と、リクエストの重さの抑え方

バージョンを、切らないという考え方

「v2を作る」ではなく、足して、古いものに印をつける。

足しても、誰も壊れない

クライアントは、自分が書いたフィールドしか受け取りません。だから型やフィールドを増やしても、いま動いているクライアントの応答は1文字も変わりません。

「どんな変更も壊れうるから、版を切る」という前提が消えます。多くのGraphQL APIがバージョンを持たないのは、これが理由です。

消すときは、まず印をつける

@deprecated(reason: "...") を付けると、開発ツールが「これはもう使わないで」と警告してくれます。データはそのまま返り続けるので、いきなり壊れることはありません。

使われなくなったのを確かめてから、はじめて消します。順番は「足す → 印をつける → 移ってもらう → 消す」。

既定でnull許容なのには、理由がある

GraphQLのフィールドは、何も付けなければ null になりえます。DBが落ちる、権限がない、外部サービスが応答しない——そのフィールドだけを null にして、残りは返せるようにするための既定値です。

! を付けるのは「絶対に返せる」と約束できるときだけ。約束したフィールドが null になると、エラーは親までさかのぼり、親ごと null になります。付けすぎると、小さな失敗で大きく欠けます。

気をつけないと、あとで困る

自由に書けるということは、自由に重くも書けるということです。

  1. N+1を、はじめに潰す。フィールドごとに関数を書ける気持ちよさの裏で、1件ずつDBに聞きに行く形になりがちです。同じ種類の問い合わせをためて1回にまとめる仕組み（DataLoader など）を、最初から入れておきます。
  2. 深さと広さに、上限を置く。friends { friends { friends … } } のような入れ子、別名を100個並べた1本のクエリ、1リクエストに何十も詰めた操作。どれも1通でサーバーを潰せます。深さ・広さ・バッチ数の上限は設定で持てることが多いので、必ず入れます。
  3. 一覧は、必ずページングする。返る件数に上限のないリストは、それだけで危険です。カーソル方式（edges / node / cursor / pageInfo）が広く使われています。
  4. ステータスコードだけを見ない。data が返っていれば、errors が入っていても 2xx で返るのが基本です。「200だから成功」と判断すると、一部だけ失敗した応答を見落とします。
  5. キャッシュの考え方が変わる。窓口が1本なので、URL単位のキャッシュが効きません。読み取りを GET で送る、あらかじめ登録した文書をIDで送る（persisted / trusted documents）、オブジェクトに全体で一意な id を持たせてクライアント側に貯める、といった別の手を使います。
  6. 認可は、リゾルバの中に書かない。「この人はこの項目を見てよいか」はビジネスロジック層に1か所だけ置き、リゾルバはそこを呼ぶだけにします。入口がGraphQLだけとは限らないからです。
  7. 本番では、教えすぎない。イントロスペクションと親切なエラー文は開発では便利ですが、本番ではスキーマの形を推測する手がかりになります。ただし止めるだけでは隠しきれないので、許可した文書だけを実行する方式と組み合わせます。

1. クエリの書き方

やさしい説明の「ほしい形を書いて送る」の部分

クエリは、入口の型（ふつうは Query）から始めて、ほしいフィールドを入れ子で並べていくだけです。オブジェクト型を返すフィールドには中身の指定が要り、スカラー型か列挙型（葉）にたどり着いたら、そこで止めます。

{
  book(id: "B-102") {
    title            # String — 葉。ここで止まる
    author {         # Author — オブジェクト型。中身が必要
      name
    }
  }
}

引数は、どのフィールドにも付けられる

RESTでは引数を渡せるのはURLとクエリ文字列の1か所だけですが、GraphQLでは入れ子の奥のフィールドにもそれぞれ引数を付けられます。スカラーを返すフィールドにも付けられるので、単位変換のような処理をサーバー側に1回だけ書いておく、といった使い方もできます。

{
  book(id: "B-102") {
    reviews(first: 2) { stars }
    price(currency: JPY)
  }
}

操作名と別名

先頭の query は省略できますが、名前を付けておくとサーバーのログやトレースで追いやすくなります。関数に名前を付けるのと同じ理由です。また、同じフィールドを違う引数で2回書きたいときは、結果のキーが衝突するので別名（alias）を付けます。

query BookCompare {
  left: book(id: "B-102") { title }
  right: book(id: "B-207") { title }
}

変数 — 文字列を継ぎ足さない

動く値は、クエリの文字列に埋め込まずに変数として外へ出します。手順は3つ。値を $name に置きかえ、操作の頭で型を宣言し、別のJSONで渡す。利用者の入力からクエリ文字列を組み立てるのは、やってはいけないことです。

query BookPage($id: ID!, $first: Int = 2) {
  book(id: $id) {
    title
    reviews(first: $first) { stars }
  }
}

# 変数は、別のJSONで渡す
{ "id": "B-102" }

変数を使うときは、操作の種類（query など）と名前の省略ができません。宣言できるのはスカラー型・列挙型・入力オブジェクト型だけです。

フラグメント — 部品ごとに、必要な項目を持たせる

同じフィールドの並びを何度も書かずにすむよう、名前を付けて切り出せます。画面の部品ごとにフラグメントを持たせ、最後に1本のクエリへ合流させるのが、実際のアプリでの定番の使い方です。

query Compare {
  left:  book(id: "B-102") { ...card }
  right: book(id: "B-207") { ...card }
}

fragment card on Book {
  title
  author { name }
}

インラインフラグメントと __typename

インターフェース型やユニオン型を返すフィールドでは、そのままだと共通のフィールドしか書けません。具体的な型のフィールドがほしいときは ... on 型名 を使います。返ってきたのがどの型かを知るには、どこにでも書けるメタフィールド __typename を足します。

{
  search(text: "図書館") {
    __typename
    ... on Book   { title }
    ... on Author { name }
  }
}

__ で始まる名前はすべて GraphQL の予約語です。__typename のほか、__schema と __type がイントロスペクションの入口になっています。

ディレクティブ — 形そのものを出し分ける

引数では値しか変えられませんが、ディレクティブを使うとフィールドを含めるかどうかを切りかえられます。仕様がすべての実装に義務づけているのは、この2つだけです。

@include(if: Boolean!)true のときだけ、そのフィールドを含める
@skip(if: Boolean!)true のときは、そのフィールドを飛ばす
query Hero($detail: Boolean!) {
  book(id: "B-102") {
    title
    reviews @include(if: $detail) { stars comment }
  }
}

2. スキーマの読み方

やさしい説明の「書ける範囲は、型で決まっている」の部分

名前のつく型は6種類です。オブジェクト型・スカラー型・列挙型・インターフェース型・ユニオン型・入力オブジェクト型。これに、型ではない修飾子が2つ（! と [ ]）加わります。

! と [ ] の組み合わせ

この2つは重ねて書けます。どこに ! が付いているかで意味が変わるので、表で覚えてしまうのが早いです。

[String]リスト自体が null でもよく、中身にも null が入りうる
[String!]リスト自体は null でもよいが、中身に null は入らない
[String]!リストは必ずある（空でもよい）が、中身に null が入りうる
[String!]!リストも中身も null にならない

どの書き方をしても「空でないリスト」は表せません。[] は常に正しい応答です。件数の下限を要求したいときは、型ではなく実行時の検査で見ることになります。

インターフェース型とユニオン型の使い分け

どちらも「複数の型のどれかが返る」ことを表しますが、性格が違います。

  • インターフェース型 — 共通のフィールドを約束させる。実装する型は、同じ名前・同じ引数・同じ返り型のフィールドを必ず持ちます。共通部分はそのまま書けます。
  • ユニオン型 — 共通のフィールドは持たない。union SearchResult = Book | Author のように、具体的なオブジェクト型を並べるだけです。だから ... on なしには何も書けません。
interface Node { id: ID! }

type Book implements Node {
  id: ID!
  title: String!
}

union SearchResult = Book | Author

フィールド名がたまたま同じだからといって、インターフェースにする必要はありません。クライアントから見て意味のあるまとまりのときだけ使います。

入力オブジェクト型 — 引数に渡すためのかたまり

引数に複雑な値を渡したいときは type ではなく input を使います。出力用の型と入力用の型は混ぜられません（出力の型を引数の型には使えません）。入力オブジェクト型のフィールドに引数を付けることもできません。

input ReviewInput {
  stars: Int!
  comment: String
}

type Mutation {
  createReview(bookId: ID!, review: ReviewInput!): Review
}

ルートの型は、名前を変えられる

Query・Mutation・Subscription は「入口である」という以外はふつうのオブジェクト型です。名前を変えたいときは schema で宣言します。ただし、慣習どおりの名前にしておくのが無難です。

説明文とコメント

型・フィールド・引数には説明文を付けられます。""" で囲むか " で1行。これはイントロスペクションで読み出せるので、開発ツールの上に表示されます。# で始まる行はただのコメントで、クライアントからは見えません。

"""本1冊"""
type Book {
  "表紙に書かれているタイトル"
  title: String!
  oldTitle: String @deprecated(reason: "title を使ってください")
}

3. リクエストの一生と、応答の形

やさしい説明の「1回のリクエストで、何が起きているか」の部分

送られた文章は 解析（parse）→ 検証（validate）→ 実行（execute）→ 応答 の順に処理されます。大事なのは、検証が実行の前に終わることです。存在しないフィールドや型の合わない変数は、DBに触る前にはじかれます。

応答のトップレベルは3つだけ

仕様が認めているキーは data・errors・extensions の3つです。data と errors の少なくとも片方は必ず入ります。両方入っている状態を部分応答と呼びます。

{
  "data": { "book": { "title": "銀河の図書館" } },
  "errors": [
    {
      "message": "レビューの取得に失敗しました",
      "path": ["book", "reviews"],
      "locations": [{ "line": 4, "column": 5 }]
    }
  ]
}

リクエストエラーとフィールドエラー

リクエストエラー構文エラーや検証エラー。実行が始まる前なので、data は入らない。クライアント側の書きまちがい。
フィールドエラー実行中に起きた失敗。ほかのフィールドの処理は続行され、取れたぶんは data に入ったまま errors が添えられる。

ここが REST と大きく違うところです。「エラーが返った＝全部だめ」ではありません。クライアントは errors の path を見て、どのフィールドが欠けたのかを判断する必要があります。

! が付いたフィールドが失敗すると

Non-Null（!）のフィールドで失敗が起きると、そこに null は入れられません。エラーは親をさかのぼって、null を入れられる場所まで上がっていきます。! を付けすぎたスキーマでは、末端の小さな失敗で応答の大部分が消えることがあります。

extensions

実装が自由に使ってよい場所です。実行時間やレート制限の残量など、サーバー側の情報を載せているAPIがあります。中身に決まりはないので、依存するときは相手の実装を確認してください。

4. HTTPに載せる

やさしい説明の「往復の回数」の部分

GraphQLの仕様は、どの通信路を使うかを決めていません。ただ実際にはHTTPが使われることがほとんどで、その作法は「GraphQL over HTTP」という別の仕様（策定中）にまとまっています。

窓口は1つ

RESTと違い、URLは資源を指しません。/graphql のような単一のエンドポイントに、すべての操作を送ります。何を取るかはURLではなく、本文に書いたクエリが決めます。

POST の本文

POST /graphql
Content-Type: application/json
Accept: application/graphql-response+json, application/json

{
  "query": "query BookPage($id: ID!) { book(id: $id) { title } }",
  "operationName": "BookPage",
  "variables": { "id": "B-102" }
}

query だけが必須です（名前に反して、中身は mutation でもかまいません）。1つの文書に複数の操作を書いたときだけ operationName が必須になります。

GET も使える（読み取りだけ）

サーバーが対応していれば、query 操作は GET /graphql?query={book(id:"B-102"){title}} のようにも送れます。GETはキャッシュされやすいので、CDNを効かせたいときの手になります。ただしURLの長さに上限があるため、長いクエリはそのままでは載りません。mutation をGETで送ることはできません。

永続化文書（persisted / trusted documents）

そこで、使うクエリを事前にサーバーへ登録しておき、実行時はそのIDだけを送るやり方が広く使われています。通信量が減り、URL長の問題も消えます。登録した文書だけを実行させれば、そのまま安全対策にもなります（後述）。

ステータスコード

  • data が null でない応答は、errors があっても 2xx。HTTPには「一部成功」を表すコードがないためです。
  • 検証エラーで実行に至らなかった場合は、ふつう 400。
  • ただし古い実装（application/json で返すもの）では、失敗しても 2xx を返すことがあります。ステータスコードだけで成否を判断しないのが安全です。

認証はGraphQLに入る前のミドルウェアで済ませ、認可（この人がこの項目を見てよいか）は実行中に判断します。そうしないと、部分応答として「見てよいところだけ返す」ができません。

5. N+1と、リクエストの重さを抑える

やさしい説明の「往復は、消えたのではなく移った」の部分

なぜ N+1 が起きるのか

GraphQLは「フィールド1つにつき関数1つ」という、とてもきれいな作りをしています。Book.author のリゾルバは、渡された本1冊の著者を取ってくればいい。だからこそ、本が20冊あればその関数が20回呼ばれ、素直に書くとDBへの問い合わせも20回になります。

{
  books(first: 20) {   # 1回：本を20冊
    title
    author {           # 20回：1冊ずつ著者を引く
      name
    }
  }
}

まとめ読み（バッチ）で畳む

解決策は、ひと呼吸ためてからまとめて聞くことです。同じ種類の問い合わせを短い時間だけ集め、WHERE id IN (…) の1回にして投げ直します。Meta（Facebook）が公開した DataLoader がこの考え方の代表で、多くの言語に同じ発想の実装があります。同一リクエスト内での重複除去（同じ著者を2回引かない）も、たいてい一緒についてきます。

実装によっては、クエリの選択集合を読んで、最初から最適化された1本のSQLに変換してくれるものもあります。

デマンドコントロール — 重すぎるクエリを断る

N+1を潰しても、「書けてしまうから重い」という問題は残ります。段階を追って手を打ちます。

ページングリストを返すフィールドには必ず件数の上限を。まずはここから。
深さ制限入れ子の段数に上限を置く。循環する関係（友だちの友だちの…）は無限に深く書けてしまう。リストの入れ子には、さらに小さい上限を別に置くとよい。
広さ・バッチ制限1操作あたりのルートフィールド数・別名の数、1リクエストに詰められる操作の数に上限を置く。浅くても、別名を100個並べれば同じだけ重い。
複雑度解析型やフィールドに重みを付け、リクエスト全体の見積もりコストが上限を超えたら実行前に断る。レート制限の単位としても使える。
信頼できる文書自社のクライアントだけに出すAPIなら、開発時に登録した文書だけを実行可能にする（trusted documents）。上の対策の多くが不要になるほど強い。

レート制限は、ネットワーク層で「1分間に何リクエスト」と数えるだけでは足りません。同じ1リクエストでも重さがまったく違うからです。ビジネスロジック層で、実際に触った量に応じて数えるのが現実的です。

圧縮と観測

応答はJSONなので、GZIPなどがよく効きます（Accept-Encoding: gzip）。また、どのフィールドが遅いか・どのフィールドがよくエラーになるかは、フィールド単位で計測してはじめて見えます。OpenTelemetry のような仕組みで、実行の中に計器を入れておくと運用が楽になります。

6. 認可・イントロスペクション・キャッシュ

やさしい説明の「気をつけないと、あとで困る」の部分

認可は、リゾルバの中に書かない

「下書きは書いた本人にしか見せない」のような規則は、書こうと思えばリゾルバの中に書けます。学習や試作ならそれで十分です。ただし本番では、その規則が入口の数だけ重複します。GraphQLのほかに管理画面のAPIやバッチがあれば、同じ判断を何か所にも書くことになり、いずれズレます。

// 判断はビジネスロジック層に1か所だけ置く
export const postRepository = {
  getBody({ user, post }) {
    const isAuthor = user?.id === post.authorId;
    return isAuthor ? post.body : null;
  }
};

// リゾルバは、それを呼ぶだけ
function resolvePostBody(obj, args, context) {
  return postRepository.getBody({ user: context.user, post: obj });
}

認証（誰であるか）はGraphQLに入る前のミドルウェアで済ませ、その結果を context に載せて全リゾルバへ渡すのが定石です。トークンのような不透明な値ではなく、解決済みのユーザー情報を渡します。

どうしてもGraphQL層に置きたい場合は、directive @auth(rule: Rule) on FIELD_DEFINITION のような型システムディレクティブでスキーマに印を付ける方法もあります。ただし、その場合も実際の判断はビジネスロジック層に委ねます。

イントロスペクションを止めるのは、目隠しにすぎない

本番でイントロスペクションを閉じるのは一般的な手ですが、これは「隠す」であって「守る」ではありません。エラーメッセージの「もしかして titel ではなく title ですか？」といった親切な示唆からも、スキーマの形は推測できます。本番ではエラーの詳細も伏せ、そのうえで許可した文書だけを実行する方式と組み合わせるのが、実効性のある守り方です。

キャッシュのための、全体で一意なID

RESTではURLがそのまま「この世に1つのキー」でした。GraphQLには対応するものがないので、APIの側から一意なIDを渡すのが定石になっています。id フィールドを全体で一意な値に決めてしまうやり方が広く使われます（型名とIDをつないで Base64 にするなど）。

クライアント側のライブラリは、このIDをキーにして受け取ったオブジェクトを1か所に貯めます。だから別のクエリで同じ本が返ってきても、同じものとして扱えます。__typename と型ごとのIDを組み合わせて、クライアント側で作る手もあります。

既存のRESTを置きかえるとき、id だけが今までと違う値になると混乱のもとです。その場合は、従来のIDを別のフィールド（legacyId など）で並べて出すと衝突を避けられます。

ページングは、コネクションで

単純な friends(first: 2) でも件数は絞れますが、「次の2件」を取るには基準になる目印が要ります。そこで、リストを直接返さず、目印（cursor）と中身（node）の組を返す形が定着しました。

{
  book(id: "B-102") {
    reviewsConnection(first: 2, after: $cursor) {
      totalCount
      edges {
        cursor       # 次はここから、を表す目印
        node { stars comment }
      }
      pageInfo {
        endCursor
        hasNextPage  # まだ続きがあるか
      }
    }
  }
}

件数指定（offset）方式に比べて、途中でデータが増えても位置がずれません。cursor は中身を推測されないよう不透明な値（Base64など）にしておくのが慣習で、そうしておけば後からページングのやり方を変えても、クライアントを直さずに済みます。
